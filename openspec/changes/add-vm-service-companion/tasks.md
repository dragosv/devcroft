## 1. Prerequisites, catalog contract and base measurement

- [ ] 1.1 Wait for `evaluate-microvm-runtimes` task 4.5 to select the VMM and record the owner's `author_claimed_security_boundary` decision before enabling the companion in production; confirm the selected VMM carries concurrent connections on per-port guest-initiated (workload) and host-initiated (companion) vsock mappings, and treat a VMM that cannot as a design change.
- [ ] 1.2 Define the trusted service catalog schema (PostgreSQL, Redis): fixed closure digest, generated configuration, durability settings (PostgreSQL `fsync`, `full_page_writes`, `synchronous_commit` on; Redis `appendonly yes`, `appendfsync always`), least-privilege client role and the authentication rules that keep every other identity off the relay, readiness probe, stop signal (`SIGINT` for PostgreSQL, `SIGTERM` for Redis), data format version and default disk size.
- [ ] 1.3 Define the `devcroft.toml` key through which a VM project requests catalog profiles by name, failing unknown names at layer `config` (exit 2); enforce the catalog boundary in provider/config resolution, routing only verified catalog profiles to the companion (verification failure at layer `provider`) and keeping provider-declared `ServiceDecl.command` services in the workload VM or refusing them by name if requested as catalog profiles.
- [ ] 1.4 Measure NixOS minimal vs. pinned closure + dedicated init on the same PostgreSQL + Redis fixture (cold boot to broker readiness, idle RSS, disk image size, fixed footprint with an initialized empty data directory) plus the throughput cost of full flush semantics and `appendfsync always`, and record the owner's base choice.

## 2. Companion guest, control channel, relay forwarder and diagnostics

- [ ] 2.1 Build the companion guest image on the pinned Linux LTS kernel with no SSH, no keeper, no login daemon, no interactive shell, no `/workspace` mount and no network interface (`NIC`/`TSI`), carrying the filesystem check tool used before mounting `companion-rw.img`.
- [ ] 2.2 Implement the host-initiated single-opcode `SHUTDOWN` control channel in companion PID 1 (vsock port below 1024, `/run/devcroft-init`, `0700`, `root:root`): accept only peer CID 2, bind to the instance generation delivered as a non-secret kernel command-line value, enforce a fixed frame cap, reject every other opcode and acknowledge completion before poweroff.
- [ ] 2.3 Implement first-boot catalog administrative setup over the companion-local Unix socket and the client roles: PostgreSQL admin roles on `peer` only, `pg_hba.conf` admitting only the client role on `host` lines and ending in `reject`, client role without superuser, program execution, untrusted languages or `ALTER SYSTEM`; Redis with the restricted `default` user as the only ACL user, refusing `CONFIG`, `MODULE`, `DEBUG`, `ACL`, `SHUTDOWN`, `SAVE`, `BGSAVE` and `REPLICAOF`, with protected-config, debug and module defaults kept disabled.
- [ ] 2.4 Implement the host-initiated diagnostic stream from companion PID 1 to a size-bounded host buffer: the companion supervisor holds the only connection, opened before any service starts on every boot; PID 1 labels service output distinctly from its own events, reserves capacity for its events, drops only service output, reports drop counts as events and never blocks `SHUTDOWN`.
- [ ] 2.5 Implement the companion relay forwarder, started by PID 1 under its own unprivileged identity, accepting per-port vsock connections only from peer CID 2 and connecting to `127.0.0.1:<port>`.

## 3. Workload listener, broker, readiness and lifecycle

- [ ] 3.1 Add the workload relay listener to the workload guest image: started by workload init before creation-time setup and on every boot, one loopback listener per declared port, each opening a guest-initiated vsock connection on that port's relay mapping; list the relay channel in the workload launch plan.
- [ ] 3.2 Implement the per-instance broker: per declared port, accept from the workload helper's mapping and open one connection to the companion's mapping for the same port; one host stream per TCP connection, half-close propagation, a finite concurrent-connection cap and per-direction buffer recorded in the launch plan and tested at the cap, stream closure across workload restarts/reboots, and launch refused for endpoints outside its own instance's controller record.
- [ ] 3.3 Run each requested profile's readiness probe from the broker before workload creation-time setup and before session/fleet admission, failing at layer `keeper` (exit 5) on timeout; map companion helper, VMM and confinement failures to `backend` (exit 4) and PID 1, channel and broker failures to `keeper`.
- [ ] 3.4 Implement graceful companion stop on `down` and restart: stop workload sessions, close all broker streams, record the stop request with the companion supervisor, which sends `SHUTDOWN`, let PID 1 stop services with their profile stop signal, sync and unmount `companion-rw.img`; classify a stop as orderly only on PID 1's acknowledgement correlated with the recorded stop intent and helper identity, never on helper exit status, and record forced stops otherwise.
- [ ] 3.5 Implement the per-instance companion supervisor and automatic restart: started by `up` with the instance's lifetime; launches each helper incarnation, holds the control and diagnostic connections and writes restart records host-side; on a crash, the broker refuses and closes streams, `status` shows restarting, the supervisor relaunches with a new boot identity, the task 4.1 recovery runs and the relay reopens after readiness; bounded backoff with count and window recorded in the launch plan; no restart after a stop request, an incompatible data format version, a filesystem check needing manual repair, a catalog verification failure or a confinement failure.

## 4. Storage durability and host confinement

- [ ] 4.1 Create `companion-rw.img` with a finite size and full flush semantics; record the profile and data format version on disk; refuse incompatible major versions at layer `provider` by name without modifying existing data; run the pre-mount filesystem check and service recovery after a forced stop or crash; report a full disk in `status`.
- [ ] 4.2 Apply in-process host confinement before the first guest instruction, stream or helper launch to the workload helper, companion helper, broker and companion supervisor (covering the companion helper's grants and nothing on the workload side), with the layout `w/`, `wr/`, `cr/`, `cc/`, `cs/` and `meta/` within the 103-byte `sun_path` limit: Seatbelt with path-limited outbound Unix-socket connections on macOS; Landlock ABI ≥ 6, `seccompiler` across all threads and a per-role user + mount namespace on Linux, measured with `/dev/kvm`, falling back to separate host UIDs, and failing closed when neither is in force.

## 6. Verification

- [ ] 6.1 Verify isolation and protocol controls: dual-VM launch when catalog profiles are requested and single-VM launch when none are; refusal of admin identities over the relay (PostgreSQL superuser, Redis `AUTH` as another user, `ACL SETUSER`); refusal of `COPY ... FROM PROGRAM`, `ALTER SYSTEM`, `MODULE LOAD` and `CONFIG SET`; no mapping for undeclared ports; refusal of a broker launched with another instance's endpoint; recovery of every write acknowledged under the profile durability settings after `SIGKILL` during active writes.
- [ ] 6.2 Verify confinement negatives on each platform row: the workload helper cannot reach `cr/`, `cc/`, `cs/` or `meta/`; the companion helper cannot reach `w/` or `wr/`; a missing seccomp filter or missing socket-reach separation fails closed; a companion-local vsock `SHUTDOWN` is refused.
- [ ] 6.3 Verify the failure paths: a service flood induced through the relay still delivers PID 1 events and drop counts and completes `SHUTDOWN`; a companion panic (helper exit status 0) is treated as a crash, not a stop, and restarts automatically through recovery with the relay reopening after readiness; repeated crashes stop at the recorded bound; a disk needing manual repair and a stop request during a restart both prevent further restarts; a full companion disk is reported in `status`.
- [ ] 6.4 Document the optional Linux diagnostic kernel profile (`CONFIG_BPF_SYSCALL`, `CONFIG_TRACEPOINTS`, `CONFIG_FTRACE`, `CONFIG_DEBUG_INFO_BTF`) separately from the default production kernel, keeping eBPF/Falco optional and non-gating.
