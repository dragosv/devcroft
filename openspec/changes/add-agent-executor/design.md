## Question

Can a supported harness send its real test command to a separate project process tree while the project has no access to the agent’s credential? Start after one recipe passes its terminal qualification. Use a fresh disposable sandbox, a synthetic credential and the project’s actual toolchain.

## Experiment

Start with a Linux fixture (`network.default = "deny"`, private mount view) and two sibling trees, separate homes and network policies, a shared workspace and a pair-specific executor. Create listeners before applying restrictions. Freeze the project's environment at startup after refusing any `[env] forward` or `[env.vars]` collision on the agent's brokered or direct (`auth = "env"`) credential variables, and verify canonicalized project/provider/tooling filesystem grants for both `Read` and `ReadWrite` (`artifact_store_write_overlap` checks `ReadWrite` only) so neither the isolated agent `HOME` nor the executor socket directory is covered by a project read grant. Compare the agent’s own runtime with project commands started by direct arguments and by the shell, including descendants. Record working directory, runtime version, exit status, cancellation and cleanup.

Repeat the edit-and-test path with one real harness. Identify the supported setting that routes project commands to the executor and whether workspace or session settings can change it. Record any local commands outside that route. Confirm that project configuration (`[env] forward`, `[env.vars]`, `filesystem.read` / `read_write`) cannot put the synthetic credential or the agent's `HOME`/socket into the project’s environment or grants, and that the project cannot reach the agent's proxy or credential route. The shared workspace still allows project files to influence the agent.

## Decision and mandatory gates for any follow-up Mode 2 proposal

Record the tested recipe/version, platform, authentication method and results. If routing or credential separation fails, retain the shared-sandbox offering and document the limit. A positive result qualifies a follow-up production Mode 2 proposal only if that proposal enforces all five non-degradable isolation gates established during review:

1. **Mandatory `network.default = "deny"` and private view:** Mode 2 is refused (never downgraded) when `network.default = "allow"` on any platform (on Linux for private mount/network namespaces; on macOS because Seatbelt mediates pathname AF_UNIX `connect()` on `network-outbound`, which `"allow"` leaves open, and because `proxy_only(project_port)` is required to block access to the agent's loopback proxy) or when Linux runs in Landlock-only fallback without a mount view.
2. **macOS `auth = "env"` ineligibility until measured:** On macOS, even if Seatbelt socket denials and `proxy_only` pass hardware verification, `auth = "env"` is ineligible in Mode 2 until `KERN_PROCARGS2` / `ps -E` cross-process environment visibility between sibling trees is measured closed (`api-key` and `login` place no real upstream secret in the agent's process environment).
3. **Pre-snapshot credential collision refusal:** Refuse `[env] forward` and `[env.vars]` entries naming any credential variable of the selected recipe across `api-key`, `login` and `env` before capturing the project environment snapshot (`src/lifecycle/up.rs`), so `env_clear` plus snapshot restore cannot re-expose the secret.
4. **Canonical `Read` + `ReadWrite` grant overlap refusal:** Check canonicalized filesystem grants across every sandbox profile against both the isolated agent `HOME` root (`~/.local/share/devcroft-agent-homes/<sandbox-id>/<recipe>/home`) and the executor socket directory, refusing `Read` as well as `ReadWrite` overlaps.
5. **Mode 1 → Mode 2 quarantine (`Meta.mode1_recipes` + `recipe.state_paths`):** Because Mode 1 stores tokens in `<project>/.devcroft/<name>/home` (retained as the project tree's `HOME` in Mode 2), switching an existing sandbox to Mode 2 for any recipe recorded in `Meta.mode1_recipes` (`add-agent-packages`) must fail while any of its `state_paths` exists in project `HOME`, move them via `O_NOFOLLOW` descriptors to an ungranted quarantine directory only on explicit `--quarantine-agent-state` (never copying Mode 1 tokens into Mode 2 `HOME`), and instruct the user to revoke the prior Mode 1 token and re-authenticate.
